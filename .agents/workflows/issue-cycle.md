# Issue Cycle Protocol (v1.2)

> v1.2 (2026-08-27 회고 반영): G1 에 «먼저 재고 계획한다» · dev 라우팅에 맥락 보유 예외 · fixed UI 실측 수치 정정
>
> v1.1 (2026-08-24 회고 반영): dev 라우팅 기준(소형은 메인 직접) · plan.accept 기본 체크 · smoke 내장 · 기획자 눈높이 보고 규칙 · 회고의 lint 질문

**입력**: `_private/sprint/{cycle}/tasks.json` (이슈 목록·우선순위·게이트 상태) + GitHub 이슈 본문
**출력**: 이슈당 커밋 1개 + tasks.json 증거 + `log.md` 회고 원료

## Phase 0 — 세션 시작
1. tasks.json 읽기. `status` 가 `done` 이 아닌 첫 항목이 현재 작업. **순서를 바꾸지 않는다** (우선순위는 plan 단계에서 확정된 것).
2. 현황 1줄 보고: `✅ n건 완료 · ⬜ m건 남음 · 다음: #N 제목`

## Phase 1 — 이슈 1건 처리 (4 게이트, 순서 고정)

### G1 plan (메인 세션)
- 이슈 본문 + 관련 코드 구간을 읽고 tasks.json 의 `plan` 을 채운다: `cause`(원인) · `change`(바꿀 것, 파일·함수 단위) · `accept`(완료 기준, 검증 가능한 문장) · `qa`(검증 절차, e2e 케이스 포함) · `docs`(lint 가 강제하는 문서 동기화 대상).
- **accept 기본 체크** (v1.1 — 되돌림 3회 중 2회가 이 유형): 위치·레이아웃을 건드리면 "ScreenSpec 자체 fixed UI(툴바 50px · 설명 패널 wrap 460px·overlay 400px · 재현 중 띠)와 겹치지 않음" 을 반드시 넣는다. 예제(examples/*.html)를 고치는 이슈면 plan 에 **배치 제약**(어디에 둘지, 기존 e2e 가 의존하는 ID·문구 유지)을 적어 서브에이전트가 스스로 판단하지 않게 한다.
- **이슈를 다 처리하는 것이 목적이 아니다.** 범용성 기준으로 판단한다 — 이 라이브러리의 계약(data-spec·설정 한 벌·단일 파일)을 바꾸거나, 특정 팀 사정에만 맞는 요청이면 구현하지 말고 `status: blocked` + 판단 요청. 판단 요청 문장은 §보고 규칙을 따른다.
- **먼저 재고 계획한다** (v1.2): 기획 문서·이슈가 「실측하라」고 적어 둔 것이 있으면 **계획을 쓰기 전에** 재고 결과를 `plan.measured` 에 남긴다. 실측이 설계를 가르는 일이 실제로 있었다 — 2026-08-27 #37 에서 「파일 접근 API 는 막혀 있지 않지만 파일 선택 창은 자동 조작이 불가능」이라는 측정 결과가, 저장 로직을 «순수 함수(자동 검증 가능) + 브라우저 껍데기(사용자 QA)» 로 쪼개는 설계를 낳았다. 계획을 다 쓴 뒤에 쟀다면 계획을 다시 썼을 것이다.
- **자동으로 검증 못 하는 것은 그때 골라낸다.** 실측으로 「이건 e2e 로 못 덮는다」가 드러나면 그 항목을 `plan.qa` 의 사용자 QA 로 옮겨 적는다 — 나중에 발견하면 이미 그 전제로 코드가 짜여 있다.
- 설계 판단이 갈리면 여기서 사용자에게 묻는다. dev 단계에서는 묻지 않는다.
- `plan.done = true` 는 위 5필드가 전부 채워졌을 때만.

### G2 dev (모델은 tasks.json `dev.model` — 아래 라우팅 기준)
- **라우팅 (v1.2)**: 예상 변경 **≤40줄·파일 1~2개** → 메인 세션이 직접(`dev.model: "main"`). 서브에이전트는 컨텍스트를 처음부터 다시 읽어 소형 수정에는 배보다 배꼽이 크다(실측: 10줄 수정에 55~91k 토큰). 그 이상이거나 CSS·UI 를 여러 지점에서 만지면 `opus` 서브에이전트. 문서만이면 메인 직접.
- **예외 (v1.2)**: 40줄이 넘어도 ① 메인이 **이미 그 코드의 맥락을 쥐고 있고** ② 변경이 **쪼갤 수 없는 한 덩이**이며 ③ 메인의 컨텍스트에 여유가 있으면 메인이 직접 한다. 40줄 기준의 근거가 「서브에이전트는 맥락을 다시 읽어야 해서 비싸다」인데, 이미 맥락을 쥔 메인에는 그 근거가 거꾸로 작용하기 때문이다. (2026-08-27 사이클: 편집·인쇄·레이어 세 건 모두 메인이 직접, 되돌림 0회)
- **그래도 서브에이전트로 보내는 경우**: 메인의 컨텍스트가 빠듯하거나(요약이 임박), 작업이 서로 안 겹치는 여러 덩이로 쪼개지거나, 맥락 없이도 명세만으로 되는 기계적 작업일 때. 위 예외는 「메인이 편하니까」가 아니라 「맥락 재적재가 낭비일 때」만 쓴다.
- 서브에이전트에 plan 을 **그대로** 전달한다. 재해석 금지, 범위 확장 금지("겸사겸사" 수정 금지).
- 완료 조건: `node tests/lint.js` 통과 + 변경 요약 회신. 새 동작은 **e2e 케이스를 반드시 추가**한다(회귀 방지가 이 사이클의 핵심).
- 회신을 `dev.summary` 에 기록. 서브에이전트가 범위를 벗어났으면 되돌리고 다시 시킨다.

### G3 qa (메인 세션)
- `git diff` 를 직접 읽어 plan.change 와 일치하는지 확인 (범위 드리프트 검사).
- `node tests/lint.js` + `node tests/e2e.js` 실행, 결과 요약을 `qa.evidence` 에 기록 (PASS/FAIL 수).
- plan.qa 의 수동 항목이 있으면 Playwright 스크립트로 실측하고 수치를 적는다.
- 실패 → G2 로 되돌린다. 3회 실패하면 사용자에게 보고.

### G4 commit (메인 세션)
- 이슈 1건 = 커밋 1개. 메시지: `{fix|feat|docs}: {한 줄 요약} (fix #N)` / 여러 이슈 한 뿌리면 `(fix #12, fix #7)`.
- `commit.sha` 기록 → `status = done`. CHANGELOG 는 사이클 끝에 한 번에 쓴다(버전 릴리스 단위).

### 규칙
- **즉시 체크오프**: 게이트 통과 즉시 tasks.json 갱신. 모아서 하지 않는다.
- **막히면 묻기**: 원인 불명·설계 분기·이슈 본문과 코드 불일치 → 사용자에게 선택지 제시. 절대 조용히 skip 하거나 "나중에" 로 미루지 않는다. 미루려면 `status = blocked` + `blocked_reason` 을 적는다.
- **log.md**: 작업 중 "프로토콜이 빠뜨린 것 / 불필요했던 것 / 통찰" 이 생기면 그 즉시 `_private/sprint/{cycle}/log.md` 에 1줄 적는다. 회고 원료.

## Phase 2 — 사이클 종료
1. 전체 QA: `node tests/lint.js` + `node tests/e2e.js` + `node tests/smoke.js`(예제 전수 클릭, v1.1 부터 저장소 내장). 결과를 tasks.json `cycle_qa` 에 기록. smoke 경고는 main 브랜치와 비교해 회귀인지 판별한다.
2. 버전 bump(헤더 주석·워터마크·문서 CDN 태그 — lint 가 정합 검사) + CHANGELOG 작성 → 커밋 1개.
2-1. **배포는 4단계다: main 머지 → 태그 push → `gh release create` → CDN purge.** 태그만 밀면 저장소 첫 화면(모바일 포함)의 버전은 갱신되지 않는다 — GitHub 은 Release 를 기준으로 표시한다. 릴리스 노트는 그 버전의 CHANGELOG 절을 그대로 쓴다. (2026-08-24: v0.14~v0.18 을 태그만 밀어 저장소가 v0.13.1 로 보였다)
3. 사용자 브리핑: 처리 목록(커밋 sha) · **사용자 QA 필요 항목**(자동화로 못 보는 것: 실제 Next.js 앱에서의 체감 등) · 보류/차단 항목 · push/PR 여부 질문. 문장은 §보고 규칙.

## 보고 규칙 — 기획자 눈높이 (v1.1)
사용자는 **기획자**다. 브리핑·판단 요청·회고는 아래를 지킨다.
- 판단 요청 1건 = ① 무엇이 문제인지 사용자 상황으로 1~2문장 ② 선택지 각각 "하면 어떻게 되는지"(기능·부작용) ③ **추천 1개와 이유**. 개발 용어(셀렉터·rAF·MutationObserver 등)는 쓰지 않거나 괄호로 쉬운 말을 붙인다. "sel+fallback 만 / text 포함 / 보류" 처럼 구현 용어로 된 선택지는 금지.
- 사용자가 결정을 미루면 추천안으로 진행하지 말고 `blocked` 로 둔다 — 단, 이슈 종료(닫기)가 아니라 "이번 사이클에서는 안 함" 이다.
- 사용자 QA 항목은 "무엇을 열어서 무엇을 눌러 보고 무엇이 보여야 정상인지" 형태로 쓴다.
4. `/ss-retro` 실행.

## 모델 라우팅
| 단계 | 모델 | 이유 |
|---|---|---|
| plan · qa(diff 리뷰·판정) · commit · 브리핑 · retro | 메인 세션 (현재 Fable) | 판단·검증은 가장 강한 모델. 세션 모델은 사용자가 `/model` 로 정한다 — AI 는 세션 모델을 바꿀 수 없다 |
| dev(코드 변경 + 테스트 추가) | 서브에이전트 `opus` | 명세가 확정된 실행 작업. 메인이 서브에이전트 모델을 직접 지정할 수 있다 |
| dev(문서만 수정) · 단순 실측 스크립트 | 서브에이전트 `sonnet` | 기계적 작업 |
| effort | max 유지 | 사용자 지정 |
