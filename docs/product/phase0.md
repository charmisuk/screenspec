## 0-1 온보딩 · `style` 설정

**스토리.** 기획자가 처음 붙일 때, AI 가 다짜고짜 쓰지 않고 프로젝트의 쓰는 법을 먼저 묻는다 — 클로드 코드가 처음에 묻는 것처럼. 답은 설정으로 남아, 다음에 AI 가 다시 쓸 때도 같은 톤이 유지된다.

**왜.** 스타일이 설정에 있어야 「AI 가 쓴 것」과 「내가 고친 것」이 같은 문법이 된다. 이슈 #24 가 열어 둔 방향이고, SKILL §4 의 어휘 뼈대(#31)가 재료다.

### 동작

1. **SKILL.md 에 「적용 전 인터뷰」 절 추가.** AI 는 적용을 시작하기 전에 아래를 묻는다 (이미 답이 대화에 있으면 건너뛴다):
   - 문구 어휘 — §4 기본 한 벌(`기본값 :` `클릭 :` …)을 쓸지, 프로젝트 어휘가 따로 있는지
   - 상태 축 — 기본(`빈 상태·로딩·오류`)을 쓸지, 프로젝트 축이 있는지 → `checklist`
   - 화면 ID 체계 — 기존 체계가 있으면 그대로 (`SCR-XXX-001` 등) → `style.idScheme`
   - 기준 폭 — 모바일인지 PC(어드민)인지 → `baseViewport`
2. **`style` 최상위 필드 신설.** 답이 남는 자리다. AI 가 읽는 계약이며, 라이브러리 런타임 동작은 바꾸지 않는다 (편집 모드·클라우드가 나중에 읽는다).

```ts
style?: {
  vocab?:    { prefixes?: string[], endings?: string[] }, // 생략 = SKILL §4 기본 한 벌
  idScheme?: string,   // 예: "SCR-{영역}-{번호}"
  notes?:    string,   // 자유 서술 — 「존댓말 금지」 「숫자는 반각」 같은 프로젝트 규칙
}
```

3. SKILL.md 의 작성 규칙이 `style` 을 우선 참조하도록 수정 — 「설정에 vocab 이 있으면 그것만 쓰고 섞지 않는다」.

### 범위 밖

- 라이브러리가 `style` 로 렌더를 바꾸는 것 (문구 검사·자동 교정 등 — 필요해지면 별도 논의)
- 웹 온보딩 화면 (Phase 1 에서 이 인터뷰의 웹판을 만든다)

### 수용 기준

- [ ] 빈 대화에서 「ScreenSpec 적용해줘」라고 하면 AI 가 위 네 가지를 먼저 묻는다 (SKILL 지시만으로)
- [ ] 답이 `style`·`checklist`·`baseViewport` 로 남고, 재적용 시 같은 톤으로 쓴다
- [ ] `docs/config.md` 에 `style` 문서화 (lint 필드 커버리지 통과)
- [ ] `style` 이 있어도/없어도/형식이 틀려도 라이브러리는 깨지지 않는다 (틀리면 콘솔 경고 1회)

### 열린 결정

- 인터뷰를 몇 문항까지 허용할지 — 4문항 초과는 온보딩이 아니라 심문이다. 기본값을 강하게 밀고 「전부 기본으로」 한 마디로 끝낼 수 있게 한다.

## 0-2 편집 모드 — Phase 0 의 심장

**스토리.** AI 가 초안을 쓴 뒤, 기획자는 정의서 패널에서 문구를 클릭해 바로 고친다. `window.SCREENSPEC` 이라는 JS 객체를 평생 보지 않는다. 저장하면 파일에 반영된다 — 서버 없이.

**왜 심장인가.** 같은 편집 UI 가 Phase 1 온라인 편집기의 몸통이 된다. 오프라인 = 파일에 저장, 온라인 = API 에 저장 — 코드는 하나, 백엔드만 다르다. 오프라인에서 편집에 익숙해진 사용자는 이미 온라인 제품의 사용법을 아는 리드다.

### 진입

- 화면정의서 모드 툴바에 **「편집」 토글**. 프로토타입 모드에서는 숨김.
- `readonly: true` 설정으로 통째로 잠글 수 있다 (전달본을 못 고치게 — inline.js 가 `--readonly` 옵션으로 심을 수 있으면 더 좋다).

### 편집 범위 (v1)

| 되는 것 | 안 되는 것 (v2 로) |
|---|---|
| 항목 `title` 수정 | 새 항목 추가 + 화면에서 요소 집어 `target` 지정 (picking UI 가 필요해 무겁다) |
| `defs` 줄의 `t`·`why`·`subs` 수정·추가·삭제·순서 | `anno` 타입 변경 · `play`/`preview`/`flowTo` 편집 (구조 지식이 필요한 필드) |
| 항목 삭제 (확인 후) | 화면(`screen`) 메타 편집 |
| `parts` 의 텍스트 필드 동일 | — |

텍스트가 편집의 8할이다 — AI 초안을 「고치는」 시나리오가 주 대상이므로 v1 은 텍스트에 집중하고, 요소 picking 은 0-2b 로 분리한다.

### UI

- 편집 토글 ON → 패널의 각 텍스트가 클릭 가능해진다. 클릭 → 그 자리에서 입력 상자로 전환(한 줄), Enter/바깥 클릭 = 반영, Esc = 취소.
- 행 hover 에 컨트롤: `+ 줄` · `+ 이유` · `↑↓ 순서` · `삭제`.
- 툴바에 **「저장」** 버튼 + 마지막 저장 시각. 미저장 변경이 있으면 배지(●)와 `beforeunload` 경고.
- 편집 중에도 마커·재생·프리뷰는 그대로 동작한다 (문서가 살아 있다는 정체성 유지).

### 저장 — 세 경로를 겹친다

1. **파일에 직접 저장** (크로미움 계열): 첫 저장에서 「프로토타입 파일을 선택하면 그 자리에 저장합니다」 → 파일 선택 → 선택한 파일에 `window.SCREENSPEC` 블록이 있는지 확인(없으면 경고) → 블록만 교체해 다시 쓴다. 핸들은 세션 동안 기억.
   - 파일 접근 API 의 file:// 지원 범위는 **구현 첫 주에 실측**한다. 막히면 이 경로는 http(s) 로 열었을 때만 노출하고 아래 폴백이 기본이 된다.
2. **다운로드 폴백** (모든 브라우저): `이름.edited.html` 로 뱉는다.
3. **설정만 복사**: 갱신된 `window.SCREENSPEC = {…}` 블록을 클립보드로 — 원본에 직접 붙여넣거나, **AI 에게 주며 「이걸로 교체해줘」** 하는 경로도 된다.

- 어느 경로든 **localStorage 초안**이 항상 깔린다: 편집 즉시 저장되고, 다시 열면 「저장 안 된 초안이 있습니다 — 이어서 / 버리기」 배너.
- 직렬화는 정해진 포맷으로 재생성한다(필드 순서 고정·들여쓰기 2칸). 원본 설정 블록 안의 주석은 유실된다 — 첫 저장 때 1회 고지.

### 수용 기준

- [ ] 코드를 한 줄도 안 보고: 문구 수정 → 저장 → 파일 다시 열기 → 반영 확인
- [ ] 다운로드 폴백 산출물이 lint·e2e 대상으로도 유효한 완전한 HTML
- [ ] 초안 복원: 저장 없이 닫았다 열면 이어서 편집
- [ ] `readonly: true` 면 편집 토글 자체가 없다
- [ ] 편집 중 마커·▶ 재생·preview 정상 (기존 e2e 전부 통과 + 편집 케이스 추가)
- [ ] 직렬화 왕복 무손실: `파싱(직렬화(config)) ≡ config` (주석 제외)

### 열린 결정

- 「저장할 때마다 새 파일」(다운로드 폴백)이 기획자에게 용인되는가 — 프로토타입 완성 직후 첫 사용자 관찰에서 최우선 확인.
- parts 추가(라벨 자동 1a·1b)를 v1 에 넣을지 — 텍스트만으로 시작하고 요청이 오면.

## 0-3 개정 (2026-08-28 피드백) — 인쇄가 아니라 **내보내기**다

기획자 피드백으로 0-3 의 전제가 바뀌었다. 원문(아래 「0-3 원안」)은 참고로 남긴다.

### 무엇이 틀렸나

**「A4 문서 한 장」이 목적지가 아니다.** 실제 목적지는 컨플루언스·노션 페이지이고,
거기서 기획자는 **이미지를 붙인 다음 그 옆에 기능 설명을 텍스트로 직접 쓴다**(또는 이미지에 같이 넣는다).
즉 우리가 만들어야 할 최소 산출물은 **표가 붙은 문서가 아니라 화면 이미지 한 장**이다.

로드맵 **D6 도 함께 고친다.** D6 은 「브라우저 의존성 0 캡처는 신뢰도가 낮아 오프라인은 인쇄(PDF)가, PNG 는 온라인 서버가 담당한다」고 적었다.
**실측 결과 그 전제가 틀렸다** — 아래 「실측」 참조.

### 실측 (2026-08-28)

DOM → SVG `foreignObject` → `<img>` → canvas → PNG. 라이브러리 추가 없이 브라우저 기본 기능만.

| 대상 | 결과 |
|---|---|
| 자체 완결 데모 (이미지가 data URI) | ✅ 720×1600(2배) · 130ms |
| `examples/shop.html` | ✅ 720×1600 · 221ms — 한글·그라디언트·이모지·그림자 전부 정상 |
| `examples/demo.html` | ❌ → **준비 세 가지 후 ✅** |

첫 실패의 원인은 이미지가 아니라 **XML 유효성**이었다. 그래서 캡처 전에 셋을 한다.

1. **주석 노드를 지운다** — 프로토타입 HTML 의 주석에 `--` 가 들어 있으면 XML 파싱이 통째로 깨진다(`-----` 구분선이 흔하다)
2. **CSS 를 `CDATA` 로 감싼다** — 안의 `<`·`&` 가 XML 을 깨지 않게
3. **여백을 준다** — 마커는 `translate(-40%,-40%)` 로 시트 밖에 걸쳐 있어, 시트만 자르면 **번호가 잘린다**(실측으로 확인)

세 가지 뒤 3/3 성공. 2배 해상도, 100~240ms, 의존성 0.

**대신 두 가지는 못 한다. 조용히 넘기지 않고 알린다.**

- **외부 주소 이미지는 백지로 나온다.** `<img>` 에 들어간 SVG 는 바깥 요청을 못 한다(브라우저 보안). `scripts/inline.js` 를 거친 파일은 이미지가 data URI 라 정상이다.
  → 내보내기 전에 `img[src^="http"]` 를 세어 **「바깥에서 불러오는 이미지 N개가 빈칸으로 나옵니다. 자체 완결 파일로 만든 뒤 뽑으세요」** 로 경고한다. 백지 이미지를 조용히 내주는 것은 실패보다 나쁘다.
- **frame 모드(iframe)는 캡처 불가.** 액자 안은 다른 문서다. 이 모드에서는 이미지 내보내기를 감추고 인쇄만 남긴다.

### 바뀐 스펙

**기본 동작 = 화면 이미지 한 장 (PNG).** 기능 설명 표는 **선택**으로 내린다.

| 선택 | 기본값 | 뜻 |
|---|---|---|
| **번호(마커)** | 켬 | 끄면 프로토타입 그림만 — 옆에 직접 쓸 때 쓴다 |
| **머리말** | 켬 | 화면 ID · 화면명 · 화면 경로 · 생성 일시를 이미지 **위쪽에 함께 굽는다** |
| **기능 설명 표** | **끔** | 켜면 이미지 아래에 표까지 한 장으로 |
| 배율 | 2배 | 1·2·3배 |

- 머리말을 이미지에 굽는 이유가 하나 더 있다: **붙여 넣은 이미지는 즉시 낡는다.** 항목 순서를 바꾸면 번호가 다시 매겨지는데 컨플에 붙인 그림은 그대로다. 화면 ID 와 생성 일시가 박혀 있어야 「어느 판의 그림인지」를 나중에 가릴 수 있다.
- **인쇄(PDF)는 남긴다.** 결재·제출처럼 「문서 한 장」이 필요한 자리가 따로 있다. 다만 **주된 길이 아니라 두 번째 길**이 된다.

### 자리 (위계 정정)

**「인쇄」 버튼을 기능 설명 패널 머리에서 뺀다.** 내보내기는 **화면 전체**에 작용하는데 「기능 설명」 패널 머리에 있었다 — 위계가 어긋난다.

- wrap: **툴바**로 (프로토타입 · 화면정의서 · IA 모드 스위치 옆). 화면 단위 동작이 모이는 자리다
- overlay: 모드 알약(pill) 옆
- 이름도 「인쇄」에서 **「내보내기」**로. 인쇄는 그 안의 한 갈래다

### 수용 기준

- [ ] 「내보내기」가 툴바(wrap)·알약(overlay)에 있고, 패널 머리에는 없다
- [ ] 기본값으로 누르면 **번호와 머리말이 있는 화면 이미지 PNG** 한 장이 나온다 (기능 설명 표 없음)
- [ ] 번호 끄기 / 머리말 끄기 / 표 켜기가 각각 산출물에 반영된다
- [ ] 마커가 잘리지 않는다 (여백 확인)
- [ ] 주석에 `--` 가 있는 프로토타입도 캡처된다
- [ ] 바깥 주소 이미지가 있으면 **내보내기 전에** 개수와 함께 경고한다
- [ ] frame 모드에서는 이미지 내보내기를 감추고 인쇄만 남긴다
- [ ] 캡처가 실패하면 백지를 내주지 않고 사유를 말하고 인쇄로 안내한다
- [ ] 인쇄(PDF)는 지금 동작 그대로 남는다

## 0-5 IA 모드 (새로 — 피드백에서)

**스토리.** 기획자는 화면을 쓰기 **전에** 화면 목록부터 그린다. IA 를 먼저 뽑아 합의하고, 그 다음 화면별 정의서를 쓴다.

세 번째 모드를 넣는다: **프로토타입 · 화면정의서 · IA**.

### 왜 이게 값이 큰가

**데이터가 이미 있다.** `screen.path[]` 가 이미 IA 경로이고(결정 D3 가 저장 구조를 여기에 맞춰 뒀다), 목차가 이미 그 트리를 그린다.
새로 받을 입력이 없다 — 있는 것을 다르게 그리기만 하면 된다.

그리고 **화면 정의를 하나도 안 쓴 상태에서도 값이 나온다.** 지금 제품은 `specs` 를 써야 쓸모가 생기는데,
IA 모드는 `screens` 만 있으면 그림이 나온다. 첫 쓸모까지의 거리가 짧아진다.

### 동작 (MVP = 보기 + 내보내기)

- `screens[].path` 를 트리로 렌더. 각 화면은 카드 — 화면 ID · 화면명 · 항목 수 · 상태 커버리지 ⚠
- 카드를 누르면 그 화면의 정의서로 간다 (모드 전환 + `setScreen`)
- **0-3 의 내보내기와 같은 경로로 이미지로 뽑는다** — IA 도면 한 장이 산출물
- 경로가 없는 화면은 「미분류」 묶음으로

### 범위 밖 (이번엔 안 한다)

- **IA 편집**(드래그로 화면 옮기기·새 화면 만들기) — 보기보다 훨씬 큰 일이다. 경로는 설정에서 고친다
- 화면 간 이동선(`flowTo`)을 화살표로 그리기 — 플로우차트는 IA 와 다른 도면이다. 요청이 오면

### 수용 기준

- [ ] 모드가 셋이 되고, `screens` 가 하나뿐인 문서에서는 IA 모드를 감춘다
- [ ] `path` 대로 트리가 그려지고 화면 카드에 ID·이름·항목 수가 보인다
- [ ] 카드를 누르면 그 화면 정의서로 이동한다
- [ ] IA 도면을 이미지로 뽑을 수 있다
- [ ] `path` 가 없는 문서도 깨지지 않는다 (미분류 묶음)

## 0-6 기능 설명 = 최소 에디터 (0-2 개정)

**피드백.** 지금 편집은 「불렛 자리를 우리가 다 잡아 주고 버튼으로 넣고 뺀다」이다. 기획자는 노션에 글 쓰듯 하길 기대한다 —
**다만 노션 전체가 아니라 «최소한의 노션»** 이다.

### 핵심 판단 — 우리는 에디터 엔진이 필요 없다

**우리 데이터가 이미 블록 모델이다.** `defs[] { t, why, subs[], layer }` 가 곧 블록 목록이다.
그래서 필요한 것은 문서 편집 엔진이 아니라 **`/` 로 정해진 스키마에 항목을 꽂는 UI** 다.

이게 중요한 이유는 **용량**이다 (기획자가 요청한 피드백).

| | gzip |
|---|---|
| 지금 ScreenSpec 전체 | **46KB** |
| ProseMirror 코어 | ~40KB |
| Quill | ~43KB |
| html2canvas | ~48KB |

**에디터 엔진이든 캡처 라이브러리든, 하나만 넣어도 라이브러리가 두 배가 된다.** 단일 파일·의존성 0 이 제품의 약속이므로 넣지 않는다.
그래서 0-3 의 캡처도 브라우저 기본 기능으로 짰고(실측 완료), 에디터도 우리 스키마 위에 직접 짠다.

**용량 상한을 못박는다: gzip 60KB.** `tests/lint.js` 가 검사한다. 넘으면 기능이 아니라 상한을 다시 논의한다.

### 동작

- 줄 끝에서 **Enter** → 같은 층에 새 줄 · **Tab / Shift+Tab** → 한 단 들여쓰기·내어쓰기 · 빈 줄에서 **Backspace** → 줄 삭제
- **`/`** → 넣을 것 고르기: `설명 줄` · `하위 줄` · `이유` · `개발 줄(DEV)`
- 항목 제목 옆 **유형 드롭다운** — 이미 있는 `anno` 8종(영역·입력·상태·동작·팝업·이동·화살표·모션). 새 필드가 아니다
- **▶ 재생·상태 재현은 라벨만 고친다.** `play.selector` 는 CSS 셀렉터라 기획자가 쓸 것이 아니다 — 그건 에이전트가 붙이고 사람은 문구만 손본다

### 데이터 — 3단까지 (하위 호환)

```ts
type Def = { t: string, why?: string, layer?: "dev", subs?: Sub[] }
type Sub = string | { t: string, subs?: string[] }   // 문자열은 지금 그대로 유효
```

`subs` 항목이 객체도 될 수 있게 열어 3단을 만든다. **기존 `subs: string[]` 문서는 한 글자도 안 바꿔도 된다.**

### 범위 밖

굵게·기울임 같은 글자 서식 · 표 · 이미지 · 드래그로 블록 옮기기 · 되돌리기 스택 · 실시간 동시편집.
전부 「최소한의 노션」 밖이고, 넣는 순간 엔진이 필요해진다.

### 수용 기준

- [ ] Enter·Tab·Shift+Tab·Backspace 가 층을 만들고 지운다 (3단까지)
- [ ] `/` 로 네 종류를 꽂을 수 있다
- [ ] 유형 드롭다운이 `anno` 를 바꾸고 마커 모양·재생 버튼이 따라 바뀐다
- [ ] `play`·`preview` 는 **라벨만** 고쳐지고 셀렉터는 편집 대상이 아니다
- [ ] `subs: string[]` 만 쓰는 기존 문서가 그대로 동작한다
- [ ] 직렬화가 3단 구조를 잃지 않는다
- [ ] **gzip 60KB 이하** — lint 가 검사한다

## 0-7 기획·개발 순서 일관성 (0-4 정정)

**피드백.** 「어떤 건 개발이 위에 있고 어떤 건 기획이 위에 있다.」 — **맞다. 우리 버그다.**

항목 **안**에서는 기획 줄 → 개발 블록 순인데, **화면 공통 개발 정의만 목록 맨 위**에 있다. 층마다 규칙이 다르다.

**규칙을 하나로 못박는다: 어느 층에서든 기획이 먼저, 개발이 나중.**
→ 화면 공통 개발 블록을 목록 **맨 아래**(상태 커버리지 바로 위)로 내린다. 개발 정의는 언제나 「번호 안, 기획 다음」이라는 한 문장으로 설명된다.

### 수용 기준

- [ ] 화면 공통 개발 블록이 목록 맨 아래에 있다
- [ ] 항목 안에서도 기획 줄 다음에 개발 블록이 온다 (지금과 같음)
- [ ] 인쇄 표에서도 같은 순서다

## 0-3 인쇄 · 화면별 PDF (#34)

**스토리.** 지금 보는 화면 하나를 종이 문서 형태로 뽑아 컨플·노션·결재에 붙인다. 브라우저의 「PDF 로 저장」이 곧 산출물이다 — 서버도 계정도 없이.

### 동작

- 정의서 헤더에 **「인쇄」** 버튼 → 작은 대화상자:
  - **범위**: 현재 화면 (일괄은 로드맵대로 뒤로 — 유료 후보)
  - **마커**: 표시 / 숨김 (숨김 = 프로토타입만 — `?screenspec=0` 상태와 같은 모습)
  - **항목 표**: 포함 / 제외
- 확인 → `@media print` 스타일이 정의서 모드를 세로 흐름으로 재배치: ① 화면 헤더(ID·화면명·경로) ② 프로토타입(시뮬레이터 스케일 해제, 종이 폭 맞춤, 마커 옵션 반영) ③ 항목 표 — 번호·영역명·유형·사양(하위 `1a`·「↳ 이유」 포함) ④ 꼬리(생성 일시 · Made with ScreenSpec) → `window.print()`.
- 다른 화면·툴바·패널은 인쇄에서 제외.

### 수용 기준

- [ ] A4 세로 기준으로 잘림·겹침 없이 나온다 (모바일 폭·PC 폭 프로토타입 모두)
- [ ] 마커 숨김 옵션이 프로토타입만 깨끗하게 뽑는다
- [ ] 긴 화면은 여러 페이지로 자연스럽게 나뉜다 (항목 행 중간 절단 금지 — `break-inside: avoid`)
- [ ] 인쇄 후 화면이 원상 복귀한다 (e2e: 인쇄 CSS 적용 전후 DOM 동일)

### 열린 결정

- 프로토타입이 A4 폭보다 넓은 PC 화면일 때 — 축소 배치 vs 가로 용지 안내. 축소를 기본으로 제안.

## 0-4 개발 정의 레이어 — 형식

**스토리.** 개발 PM 이 화면·항목 옆에 개발 정의(정책·API·이벤트)를 적는다. Phase 0 에서는 **형식(데이터·렌더·필터)까지만** — 두 사람의 동시 작성·서명·이력은 Team(Phase 2)이다.

### 데이터

```ts
type Def = { t: string, subs?: string[], why?: string, layer?: "dev" }  // 생략 = 기획
type Screen = { …, dev?: Def[] }  // 항목에 안 붙는 화면 공통 개발 정의
```

줄 단위 `layer` 로 둔다 — 한 항목 안에 기획 정의와 개발 정의가 섞이는 게 실무의 실제 모습이라서다.

### 렌더 (결정 D2)

- 항목 행 **안에** `layer:"dev"` 줄들을 「개발」 블록으로 묶어 표시 — 하위 요소(1a·1b)와 같은 들여쓰기 문법, **다른 보더 색 + `DEV` 태그**. 탭으로 가르지 않는다: 개발 정의는 기획 정의를 보면서 쓰는 글이다.
- 화면 공통(`screen.dev`)은 화면 헤더 아래 「화면 공통 · 개발」 블록 하나.
- 패널 헤더에 필터 칩 **전체 | 기획 | 개발** — 리뷰어(상사)는 기획만, 개발자는 개발 포함으로 본다. 기본값 전체.
- 인쇄(0-3)·향후 내보내기의 「레이어 선택」과 같은 축을 쓴다.

### 수용 기준

- [ ] `layer:"dev"` 줄이 항목 안 개발 블록으로, `screen.dev` 가 화면 공통 블록으로 렌더된다
- [ ] 필터 칩이 동작하고 숨김 상태가 마커·경고 로직에 부작용을 주지 않는다
- [ ] `docs/config.md` 반영 (lint 통과) · 편집 모드(0-2)에서 개발 줄도 텍스트 편집이 된다
- [ ] `layer` 없는 기존 문서는 아무 변화가 없다 (하위 호환)

### 열린 결정

- 개발 정의에 구조 필드(API 경로·이벤트명)를 줄지 — **자유 텍스트로 시작**한다. 형식은 쓰는 걸 본 뒤에.
